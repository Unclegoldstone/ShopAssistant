# Chapter 02 开发记录：Function Calling 数据查询能力

## 2026-09-29 — Superpowers / Brainstorm 启动

- 用户关键原话：“使用 Function Calling 让模型自己决定调用什么工具，工具链要在客服聊天本身内置，用户只需要在聊天页提问即可触发。”
- 用户限定：FastAPI + SQLAlchemy + Docker MySQL + LangChain `@tool`；四张表为 `faq`、`conversations`、`messages`、`tickets`；五个业务工具；单轮工具调用后收敛；不做 Agent Loop、向量检索或 RAG。
- 现状勘察：当前后端使用 FastAPI lifespan 创建单例模型与内存 `ConversationStore`；聊天入口为 `/v1/chat/completions`，采用 OpenAI 风格 SSE；前端仅消费 `delta.content`。现有请求只有 `conversation_id`，没有认证或 `user_id` 来源。
- 兼容性约束：保留当前聊天 URL、请求主体和最终逐 token 输出；新增工具事件供前端虚线框展示；持久化层将替代内存会话历史，但继续执行历史裁剪和 token 预算。
- 官方文档核对：FastAPI 当前推荐 lifespan 管理共享资源、`yield` 依赖管理数据库会话；SQLAlchemy 2.x 官方提供 `create_async_engine`、`async_sessionmaker`，MySQL asyncio 官方方言支持 `mysql+asyncmy`；LangChain 当前 `@tool` 从函数签名生成参数 Schema，`bind_tools` 产生标准化 `tool_calls`，工具结果通过带相同 `tool_call_id` 的 `ToolMessage` 返回模型。
- 待澄清：`conversations.user_id` 在当前无登录系统中如何产生；用户需求中的 `query_fag` 按验收语义暂理解为拼写修正后的 `query_faq`，待 spec 中明确。

## 2026-09-30 — Superpowers / 会话时间改为北京时间

- 用户关键原话：“目前的时间和北京时间对不上，我需要你 +8 小时，把它变成北京时间”。
- 原因确认：MySQL 容器 `@@system_time_zone` 为 UTC，消息 `created_at` 使用无时区 `DATETIME + now()`；FastAPI 返回的 ISO 字符串没有 `Z` 或偏移量，浏览器原先把它当成本地时间解析，因此没有执行 UTC → 北京时间的 8 小时转换。
- 方案：保留数据库 UTC 数据和会话列表 `MAX(messages.created_at)` 计算方式，不迁移、不改历史数据；前端将符合后端格式的无时区时间显式标记为 UTC，再通过 `Intl.DateTimeFormat` 的 `timeZone: "Asia/Shanghai"` 输出北京时间。已有 `Z`/偏移的标准时间不重复追加时区。
- 官方接口核对：实现前查阅 MDN 官方 `Date.parse`/日期时间字符串格式说明及 `Intl.DateTimeFormat` 的 `timeZone` 选项，确认无偏移日期时间的解析规则和 IANA 时区用法。
- 测试先行：新增 Node 内置测试，首次按预期因 `src/time.js` 不存在而失败；实现后验证无时区 UTC、显式 `Z` UTC和非法时间三个场景，结果 `3 passed`。
